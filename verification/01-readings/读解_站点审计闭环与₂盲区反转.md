> 性质：对「审计的审计」——核实第三方读解指出的问题，逐条判定成立/不成立，并定位一处读解自身的盲区。

## 三、B 类查证：读解「未能复现」实为读解自身的盲区

第三方读解称边数（752,647）与 level0（5,927）「未能复现」（其重算得 719,599 / 6,257），暗示可能是本站错。经查证，**是读解错、本站对**。

### 根因：读解正则漏掉了所有 `₂` 模块

读解脚本 `verify_dag.py` 的 import 正则字符类为 `[A-Za-z0-9_.']`（**纯 ASCII**），而本项目有 **394 个模块名含 Unicode 下标 `₂`**（如 `Geometry₂.GagaSections`、`Divisors₂.DenseInterior`）。这些 import 行全部被漏匹配。

### 证据

| 口径 | import 语句数 |
| :-- | --: |
| 读解正则（全文） | 876,086 |
| 本站 `startswith('import ')` | 909,822 |
| 差 | **33,736**（≈边数差 33,048） |

读解漏掉的样本**无一例外含 `₂`**。读解自己附录「已知的坑」第 3 条写「bytes 正则不能含非 ASCII → 用 `[A-Za-z0-9_.']`」——它正是为规避 SyntaxError 而牺牲了 `₂`，踩进盲区。

### 判定

| 指标 | 本站/产物 | 读解重算 | 结论 |
| :-- | :-- | :-- | :-- |
| 边数 | **752,647** ✅ | 719,599 | 本站对，读解漏 3.3 万条 `₂` import |
| level0 | **5,927** ✅ | 6,257 | 本站对，读解漏 `₂` 依赖导致虚高 330 |

### 本站的附加小口径（可修）

本站脚本有 16KB 头部限制：11 个文件的 import 在 16KB 之后（全文口径 753,261 vs 16KB 口径 752,649，差 612 条边）。产物 752,647 接近 16KB 口径。这是**可修的小口径问题**，不影响「本站对、读解错」的结论，但后续若重算应改为读全文。

## 四、经验教训

1. **「独立重算」不等于「一定对」**：第三方读解方法论扎实（标准库、不联网、流式、三方对表），但一个正则字符类的 ASCII 限制就足以让边数/level0 两个指标整体偏差 4%+。审计结论同样需要被审计。
2. **非 ASCII 标识符是 Lean 项目的常见陷阱**：本项目 394 个 `₂` 模块是下游自动生成命名，任何「模块名只含字母数字下划线点」的假设都会踩坑。
3. **口径三要素都要写清**：读文件范围（16KB vs 全文）、前缀处理（public/meta import）、字符集（ASCII vs Unicode）。三方对表前若不统一这三条，差异就无从定位。
4. **本站 16KB 限制应修复**：结构测绘脚本 `analyze_deps.py` 的 `fh.read(16384)` 是历史遗留，Lean 的 import 虽在文件顶部，但 394 个 `₂` 文件里仍有 11 个超长 import 块被截断。重算时应读全文。

## 五、结论

- 第三方读解指出的 **A 类 6 处确凿错误，本站已全部回改**（gh-pages `ce7d2115f`）。
- 第三方读解自身的 **B 类 2 处「未能复现」，实为读解正则 `₂` 盲区，本站数字正确，无需改动**。
- 本站一处 16KB 小口径问题已记录，留待结构测绘脚本重算时修复。

一句话：**审计本身经得起审计——6 处实错已修，2 处「疑错」经查证是审计方盲区，本站站得住。**
