## 三、`₂` 盲区：一个字符类拖垮四个指标

### 根因

第三方读解第一轮脚本 `verify_dag.py` 的 import 正则字符类为 `[A-Za-z0-9_.']`（**纯 ASCII**），而本项目有 **394 个模块名含 Unicode 下标 `₂`**（如 `Geometry₂.GagaSections`、`Divisors₂.DenseInterior`）。这些 import 行全部被漏匹配。

**关键：本项目的结构测绘产物 `closure_stats.txt` 同样用了漏 `₂` 的旧脚本**，于是「读解重算」与「项目产物」**共享同一个盲区、一致地错**——这是我第一轮把闭包数判反的直接原因：两个独立来源都指向 174,76x，唯独页面 175,186 孤立，我把「多数一致」误当成了「对」。

### 独立复算（IP47，全文 + 含 `₂`，split 按空白）

| 指标 | 页面/正确值 | 产物/读解第一轮 | 判定 |
| :-- | :-- | :-- | :-- |
| Main 传递闭包 | **175,186**（仅 Main 在外） | 174,764 / 174,766 | 页面对，产物+读解漏 `₂` |
| 边数 | **752,647**（16KB 口径） | 719,599 | 站对，读解漏 `₂` |
| 全文边数 | **753,261** | — | 16KB 截断漏 11 文件 612 条边 |
| level0 | **5,927** | 6,257 | 站对，读解漏 `₂` 虚高 |

### 两个独立的缺陷，别混为一谈

1. **`₂` 盲区（读解 + 项目旧产物共有）**：ASCII 字符类漏掉 `₂` import，导致闭包数偏低（174,76x vs 真值 175,186）、边数偏低、level0 虚高。**这是主要缺陷，直接影响三个指标。**
2. **16KB 截断（项目脚本 `analyze_deps.py` 独有）**：`fh.read(16384)` 漏掉 11 个文件的尾部 import（612 条边）。闭包数受影响较小（因这 11 个文件的尾部依赖大多可经其他路径到达 Main），但边数精确值应为全文口径 753,261。

两者叠加，解释了为什么「页面 175,186」与「产物 174,764」不一致：**页面是对的（早期全文含 `₂` 测绘），产物是错的（漏 `₂` 旧脚本）。**

## 五、经验教训

1. **「两个独立来源一致」≠「对」**——若它们共享同一个盲区（本例：ASCII 字符类），会一起错，而唯一「孤立」的那个才是对的。先怀疑自己的字符集，再怀疑别人的数字。
2. **非 ASCII 标识符是 Lean 项目的常见陷阱**：394 个 `₂` 模块是下游自动生成命名，任何「模块名只含字母数字下划线点」的假设都会踩坑。正确解法是 `\S+`（bytes 模式可匹配任意非空白字节，含 UTF-8 多字节），既避开 SyntaxError 又不丢 Unicode。
3. **口径三要素都要写清**：读文件范围（16KB vs 全文）、前缀处理（public/meta import）、字符集（ASCII vs Unicode）。三方对表前若不统一，差异就无从定位。
4. **审计结论同样需要被审计**：第三方读解第一轮方法论扎实，仍因一个字符类偏差 4%+；我方第一轮也因「多数一致」的先验误判闭包数。双向复算（读解第二轮 `\S+` 重跑 ↔ 我方 IP47 独立复算）最终收敛到唯一正确值。
