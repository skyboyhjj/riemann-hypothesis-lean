## 三、关键发现

1. **`/data/analyze_deps.py` 实为分层报告脚本**（SRC 指向不存在的 `/root/...`），并非闭包产物生成器；原闭包脚本已不在服务器。本轮新写 `gen_closure.py`（IP47 `/data/gen_closure.py`，本仓库 `04-scripts/gen_closure.py`）完成全文口径重生成。
2. **两个口径要分清楚**：边数用「去重」（distinct `(importer → imported)` 对 = 753,261），fan-in 用「不去重」（import 出现次数 = 3088 等）。不写清口径，同页并列就会自相矛盾。
3. **`₂` 盲区只影响旧产物，不影响现存脚本**：服务器现存脚本的 import 解析本就是 `split()`（已兼容 `₂`），真正的坑是 16KB 截断 + 旧闭包脚本的 ASCII 字符类（旧脚本已删、无从直改，故重写）。

## 四、经验教训

1. **口径三要素缺一不可**：读文件范围（16KB / 全文）、去重与否（边数去重 / fan-in 不去重）、字符集（ASCII / Unicode）。本轮「边数去重、fan-in 不去重」若非读解点破，极易混成一个数。
2. **「重文件」判定要看日志性质**：`full_build_stdout.log`（初始全量构建）会把依赖加载时间算进单文件，`>100s` 能捞出 1401 个；按层构建口径才是 95 个。重文件名单不随 import 口径变化，只需重算 fan-in。
3. **脚本的「名」≠ 脚本的「职」**：`analyze_deps.py` 名字像闭包分析，实际是分层报告。改脚本前先确认它到底产出哪个文件，别按文件名想当然。
4. **产物与页面要同源同口径**：本轮之前「一起错」（都用了截断口径），页面对了产物还错——只要产物没重生成，矛盾就一直挂着，而「下载后可按 sha256 核对」恰是本项目最看重的承诺。

---

## 五、一句话

**口径是复算的契约：边数去重、fan-in 不去重、全文读取、`split` 兼容 `₂`——四者写进脚本，页面与产物才不会再打架。**
