# RH 独立复现验证 — 核心经验与方法论

> 对象：`riemann-hypothesis-lean`（175,187 模块的黎曼猜想 Lean 4 形式化）
> 日期：2026-11-25
> 定位：从「IP121 编译失败 → 申购 IP47 → 全量零错误 → 公理审计定论」全流程中，提炼可复用的核心经验。

---

## 一句话总评

这次验证的最大收获不是「跑通了编译」，而是**纠正了一个根本性的误判**：把「资源瓶颈」误当成了「代码/方案问题」。一旦分清这一点，剩下的都是工程纪律——**先数规模、线性估内存、依赖分层、受控并行、脚本化、一句话定论**。

---

## 核心经验 TOP 8（按重要性排序）

### 经验 1：先分清「资源问题」还是「方案问题」——这是本项目的头号教训

- **现象**：IP121 编译两次中断——`no space left on device`、`GelfandPs` exit 139（SIGSEGV）。
- **一度误判**：当成代码/方案问题，去调 `--tstack`（栈）、去想「分步分包」绕过。
- **真实根因**：磁盘 139.8 G vs 全量 ~1.2 TiB（差 8 倍）；内存 14 GiB vs 4 路并行 ≈ 26 GB（堆耗尽）。
- **可复用规则**：**编译失败先查 `df -h` / `free -h` / `dmesg`，对照已知峰值判断，再决定改不改方案。** 资源不足时，任何「更聪明的分组」都救不了。

### 经验 2：先数清楚规模，再启动编译（一分钟定生死）

- **现象**：差点拿 ninja 计数器懒加载的中间值 19,850 当全量总数，做出「97.5% 已完成」的错误结论。
- **实测真实总数**：`find src -name '*.lean' | wc -l` = **175,187**，与权威 RH/VERIFY 精确吻合。
- **可复用规则**：**任何编译启动前，先数模块数、查资源（free/df），对照已知峰值判断可行性。**

### 经验 3：内存需求是线性的，按「每文件 ≈ 6.5–10 GB」估算并行度

- **实测**：单重文件 elaborate 阶段峰值 ~6.5 GB（`GelfandPs` = 6,651,544 KB）；轻模块 ~0.8 GB。
- **推论**：并行度上限 = 可用内存 ÷ 10 GB（保守）。
  - 14 GiB → 串行（~37 天，不实用）
  - 64 GiB → 6–8 路
  - 128 GiB → 12–16 路 ✅
- **可复用规则**：**内存是首要约束，CPU 其次；先定内存，再配 CPU（128 GiB ≈ 32 核即可）。**

### 经验 4：「分步分包」看着合理、实际无效；正确做法是「依赖分层 + 层内降并行」

- **错误前提**：以为 11 个 `lean_lib` 是严格分层的依赖边界。
- **真相**：`lean_lib` 只是命名空间组织，`import` 是 DAG 不是分层——任何分组都会被「穿透」。
- **正确做法**：解析全部 import 边 → Kahn 拓扑 203 层、0 循环依赖；逐层编译（层内无依赖可全并行），**重文件层降 jobs**（8–12），而非把重文件抽成单独阶段。
- **可复用规则**：**先摸依赖 DAG，按「依赖闭包/拓扑层」切分，不按目录名分组。**

### 经验 5：并行控制的两个坑（Lake 5.0）

- **坑 A**：Lake 5.0 **已移除 `-j` 选项**，文件级并行用 `lake -K jobs=N`。
- **坑 B**：`LEAN_NUM_THREADS=1` 会把文件级并行**压成串行**，反而更慢。
- **可复用规则**：**并行度只由 `lake -K jobs=N` 控制，勿碰 `LEAN_NUM_THREADS`。**

### 经验 6：远程命令一律脚本化，规避引号坑

- **现象**：Windows→ssh→bash 多层引号丢失（`grep "no space"`、`|` 等被拆）。
- **对策**：复杂命令写成脚本，scp 上传 + `bash` 执行，彻底规避。
- **可复用规则**：**远程执行一律脚本文件，不写长内联命令。**

### 经验 7：监控用「活性 + 计数」，不逐行盯

- **做法**：watchdog 用 stdout 日志 mtime（30 分钟未更新且未完成才告警），配合 `grep -c 'error:'` 计数。
- **教训**：`pgrep` 匹配进程名受 SSH 会话重置干扰会误报。
- **可复用规则**：**后台任务看「活性 + 错误计数」，不靠 pgrep、不逐行盯。**

### 经验 8：定论标准一句话

- **标准**：`#print axioms riemannHypothesis` 输出**仅** `propext` / `Classical.choice` / `Quot.sound`（及宇宙变体）即通过——方案 2，零额外 axiom。
- **陷阱**：日志曾出现一次「非常规公理」误报，实为审计解析器不识别 `Classical.choice.{u}` 的宇宙限定写法，**非源码问题**。
- **可复用规则**：**定论只看 `#print axioms` 的精确输出，先排除解析器误报再下结论。**

## 方法论沉淀（可复用 SOP）

| 步骤 | 命令/动作 | 说明 |
|------|----------|------|
| 1 数规模 | `find src -name '*.lean' \| wc -l` | 先确认全量模块数 |
| 2 查资源 | `free -h` / `df -h` | 对照峰值（内存 ~6.5G/文件、磁盘 ~1.2TiB）判断可行性 |
| 3 冒烟测试 | `import Mathlib` 单文件编译 | 验证工具链 |
| 4 依赖分层 | 解析 import 边 → Kahn 拓扑 | 按层编译，非按目录分组 |
| 5 受控并行 | `lake -K jobs=N` | 重文件层降 N；勿设 `LEAN_NUM_THREADS=1` |
| 6 远程执行 | 脚本 scp + bash | 规避引号坑 |
| 7 活性监控 | stdout mtime + `grep -c 'error:'` | 不逐行盯 |
| 8 定论 | `#print axioms <定理>` | 仅 3 条内核允许项即通过 |

## 反直觉/易错点清单

- ❌ 「分步分包能早失败」→ 底层库实测零错误，「早失败」诉求根本不触发。
- ❌ 「编完即删能控磁盘」→ 增量编译下上层 import 下层需保留下层 `.olean`，删不了。
- ❌ 「重文件集中在某一层」→ 95 个重文件散布 level 0–66，应逐层识别、遇重文件降并行。
- ✅ 「重文件是计算叶子，不是枢纽」→ 高 fan-in 是浅层轻量结构模块（逻辑骨架），重文件是低 fan-in 的计算末端。

## 迁移教训（IP121 → IP47 的本质）

一句话：**「资源瓶颈误判为代码/方案问题」的纠正过程。**

| 维度 | 误判 | 正解 |
|------|------|------|
| SIGSEGV | 以为是证明/语法错误 | 堆内存耗尽（4 路 ≈ 26G > 14G），降并行 + 扩容 |
| 磁盘满 | 以为是中间态未清理 | 全量 ~1.2 TiB 硬需求，扩容数据盘 |
| 分步分包 | 以为能绕过资源限制 | 依赖 DAG 交叉穿透，改为资源控制 |
| 模块数 19,850 | 误当全量 | `find src -name '*.lean'` 实测 175,187 |
