## 二、技术经验（最痛的三课）

**1. SSH 长任务必须 `nohup` 分离**
第一次重放 30 模块，SSH 连接断开（SIGHUP）连带杀掉远程 runner，恰好死在模块 16——前 15 个已 OK，白跑一半。第二次改用 `nohup bash ... > log 2>&1 &` 分离才跑完。
> 教训：任何 >2 分钟的远程任务，一律 `nohup ... &` 分离 + 独立 poll，别让 SSH 会话生命周期绑架任务。

**2. leanchecker 定位必须写清「同内核 vs 独立内核」**
leanchecker 是**同内核重放**（排除 elaborator/metaprogram 的 environment hacking），不是 Sutherland 的**独立内核**（TCB 层）。不写清这个边界，会被误读成「做了独立内核验证」。落盘与站点都显式标注了这层区分。

**3. 定向重放的充分性靠「论证」而非「穷举」**
全量 175k 模块重放需 7–14 天（不可行）。但「0 `unsafe` 扫描」论证了元程序无法绕过内核 → environment hacking 只能藏在自定义宏/`addDecl` 里 → 定向重放 30 个模块即封死。这是「用静态分析封死穷举需求」的典型打法。

## 三、口径与诚实

**双机交叉「20 → 14 → 6」的核实**：
- 计划写「20 模块」，实际只有 14 个可逐字节比对（6 个因 olean 嵌入绝对路径不可比）。
- 6 个「不可比」不是失败——是 Lean 4.33.1 已知行为（linter 告警嵌入源文件路径，两机构建目录不同）。
- 选择「诚实文档化」而非「凑 20/20」：站点如实写「20候选/14可比/14/14一致/6不可比」并列出 6 个模块名。
> 教训：**口径数字必须回原产物核实，宁可写成「14/14 可比」也不含糊成「基本一致」**。与之前「模块数 19,850 → 175,187」纠偏同一条原则。

## 四、工具链/环境坑（可复用清单）

1. **PowerShell 5**：`&&`/`||` 不兼容；`Select-Object -First 1` 返回 exit -1（误报失败，实际 git 已成功）；CRLF 导致 git 假改动（6 个 HTML 里只有 2 个真实改动，需 `git diff --stat` 甄别）。
2. **站点与仓库分离**：站点源在 workspace root `site/`（不在 repo），部署走 `git worktree` 流程（copy → commit → push → remove），不能直接 commit 到 custom。
3. **`lake env leanchecker` 启动开销**：每次调用 ~1 模块/分钟（顺序），30 模块 ~30 分钟；可并行（xargs）提速。
