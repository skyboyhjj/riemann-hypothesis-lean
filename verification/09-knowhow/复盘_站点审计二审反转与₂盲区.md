# 复盘：站点第三方审计的二审反转 与 `₂` 盲区

> 归档日期：2026-11-27 · 分类：方法/经验 · 关联读解：`01-readings/读解_站点审计闭环与₂盲区反转.md`
> 触发：第三方读解对我方 RH/VERIFY 站点的独立数字审计，我方一审判反了闭包数，二审（双向独立复算）反转。

---

## 一、过程三步

1. **第三方读解**：用 6 个脚本独立重算站点数字，指出 8 处问题（6 处「错」＋ 2 处「未能复现」）。
2. **我方一审**：发现读解 import 正则的 `₂` 盲区，边数/level0 判对（我方对、读解错）；但闭包数判反（把「页面对、产物错」说成「页面错、产物对」），并把对的页面数字改错了。
3. **二审反转**：读解作者用 `\S+` 修正正则重跑，我方 IP47 用 `split` 全文独立复算——两个独立实现收敛到同一值 175,186，确认页面对、产物错。回滚页面，重写读解文档。

---

## 二、五条核心教训

### 1. 「两个独立来源一致」≠「对」——共享盲区会一起错

读解重算（174,766）与项目产物（174,764）都指向 174,76x，唯独页面（175,186）孤立。我方按「多数一致」判页面错。但读解脚本与项目旧产物**共享同一个 `₂` 盲区**（都用了 ASCII 字符类），一致地错；唯一「孤立」的页面才是对的。

> 判据：先怀疑**共享的工具链/假设**，再怀疑「孤立」的少数。

### 2. 定位到一个根因后，必须全量排查它的影响面

我方发现 `₂` 盲区，用它解释了边数/level0 两个差异，却没追问「闭包数是否也受 `₂` 影响」——闭包数正是被同一盲区拖垮的**第四个**指标。根因 → 下游量的映射要列全，逐一复查，不能只查「眼前这两个」。

### 3. 自家产物 ≠ 权威锚点

`closure_stats.txt` 是项目 Release 产物，我方天然信任它，其实它是漏 `₂` 的旧脚本生成的。脚本有 bug，产物就错。复算要回到「正确算法 + 完整数据」，不迷信任何一份「官方数字」。

### 4. 非 ASCII 标识符是 Lean 项目的系统性陷阱

本项目 394 个模块名含 Unicode 下标 `₂`（下游自动命名），任何「模块名只含字母数字下划线点」的假设必踩坑。正确解法：正则用 `\S+`（bytes 模式匹配任意非空白字节，含 UTF-8 多字节），或按空白 `split()`，不要限定字符类。

### 5. 双向独立复算收敛才是终审

读解作者（正则 `\S+`）↔ 我方（`split` 按空白）是两个独立实现，最终收敛到同一值 175,186——这才是可靠判定。单方复算都不可尽信。

## 四、遗留待办（脚本与产物修复）

真正要修的是**生成产物的旧脚本**，而非页面：

1. `analyze_deps.py`：`fh.read(16384)` → 读全文；字符集改 `\S+`（或保持 `split` 按空白即可，但须读全文）。
2. 重生成 `closure_stats.txt` / `main_closure.txt` / `pivot_modules.txt` / `heavy_in_closure.txt`。
3. 重打 `grh-artifacts.zip`（sha256 会变，下载页需同步）。
4. fan-in Top5 重算（全文口径第 4/5 名被 `₂` 模块引用改变：2460 `AutomorphicForms₂.ExistsNormLeHeightPow` / 2390）。

## 五、一句话

**这场双向审计的终局是「页面站得住，要修的是生成产物的旧脚本」；而最该记住的是——发现别人盲区时，也要警惕自己踩进同类的「多数一致」盲区。**
